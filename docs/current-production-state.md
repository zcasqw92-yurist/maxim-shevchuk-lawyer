# Текущее состояние production

Актуально на 4 августа 2026 года. Это основной источник истины о текущей опубликованной конфигурации. Исторические отчёты и старые инструкции сохраняются только для контекста и не должны использоваться вместо этого файла.

## Публичный адрес и сборка

- основной канонический домен: `https://yuristshevchuk.com`;
- сайт публикуется из корня домена через GitHub Pages;
- 39 канонических содержательных URL: главная, каталог и семь страниц услуг, раздел и двадцать три юридических разбора, раздел и два полных кейса практики, страница о юристе, контакты и политика конфиденциальности;
- дополнительно генерируются две страницы-переадресации и `404.html`;
- точный опубликованный commit указывается в `build-info.json` и метатеге `site-build-sha`;
- папка `dist` создаётся сборкой и вручную не редактируется.

## География услуг

География разделена на место офиса и территорию оказания услуг:

- физический офис: Московская область, Химки, улица Горшина, 2;
- юридические услуги оказываются клиентам из Москвы и всей Московской области;
- дистанционная работа доступна по всей России, если личное присутствие не требуется.

Эта логика должна одинаково отражаться в видимом тексте, метаданных, JSON-LD, кабинетах поисковых систем, картах и будущих материалах. Адрес офиса не означает наличие офиса в Москве.

## Статус связи

Статус «онлайн» рассчитывается по московскому времени:

- онлайн: ежедневно с 08:00 до 23:00 МСК;
- офлайн: с 23:00 до 08:00 МСК;
- в офлайн-состоянии диалог выбора мессенджера сообщает, что ответ будет после 08:00 МСК.

График офиса остаётся отдельным параметром: ежедневно с 08:00 до 22:00 по предварительной записи.

## Модель обращения и персональные данные

На сайте действует модель прямого обращения без сбора контактных данных через веб-интерфейс:

- отсутствуют формы заявки, заказа звонка и обратной связи;
- отсутствуют поля имени, телефона, адреса, свободного текста и загрузки документов;
- удалены callback-форма, анкета и квиз с пользовательскими ответами;
- сайт не отправляет обращения на собственный сервер, в CRM, почту или базу данных;
- все CTA открывают единый диалог выбора Telegram или WhatsApp;
- ссылка содержит заранее заполненный черновик сообщения;
- посетитель может изменить, удалить или не отправлять черновик;
- оператор получает сведения только после самостоятельного нажатия «Отправить» во внешнем мессенджере;
- предзаполненный текст сохраняется как удобство, но не передаётся оператору до отправки пользователем.

Политика конфиденциальности подробно разделяет техническую доставку сайта, аналитику по согласию, переход к внешнему сервису и дальнейшую обработку уже отправленного обращения.

## Редакционный конвейер

Статьи и полные кейсы публикуются из `src/editorial-data.mjs`. Перед сборкой выполняется редакционный шлюз публикации. Он проверяет уникальность ID и slug, статус `published`, полноту структуры, даты, официальные источники, связи с услугами, статьями и кейсами, а также запрещает публикацию незавершённых данных.

Каждая статья автоматически получает:

- содержание, короткий ответ, официальные источники и авторский блок;
- блок самопроверки и подсказку, что подготовить для первого сообщения;
- блок «Что написать юристу»;
- оценку полезности без персональных данных;
- прямой CTA в Telegram/WhatsApp;
- Article, Person, LegalService, BreadcrumbList и WebPage;
- RSS-discovery и включение в редакционные карты сайта.

Сборка создаёт `editorial-publications.json`. Это машинно-читаемый список опубликованных статей и кейсов, который используется для контроля production и станет базовым контрактом будущей админки.

Порядок штатной публикации описан в `docs/PUBLISHING.md`.

## Эталон подготовки контента

До любой правки видимого контента используется актуальная Google-таблица `1W4014FzdUJWYDja7VUh5XXUsSuxtQIrcS5fWRX1rm24`. В начале каждой контентной сессии динамически получается полный список вкладок, после чего проверяется каждая вкладка, её используемый диапазон, заметки и контрольные показатели.

Процесс закреплён на уровне репозитория:

- `AGENTS.md` содержит обязательные инструкции для исполнителя;
- `config/content-governance.json` хранит машинный контракт и базовый перечень вкладок;
- `docs/content-governance.md` описывает назначение всех вкладок и последовательность работы;
- `reports/content-sessions/latest.json` обязателен в том же наборе изменений, что и контент;
- `npm run test:content-governance` блокирует изменение контентных файлов без актуального manifest;
- `npm run check` запускает контентный шлюз первым, затем полный набор проверок сайта.

Наличие записи в `02_ЮрДоки` подтверждает оплаченную юридическую работу, но само по себе не подтверждает точную сумму, дату и способ оплаты или положительный исход дела. Поисковые гипотезы из языка клиента становятся контентным кластером только после внешней проверки. Для кейсов выполненная работа, результат процедуры и результат дела проверяются раздельно.

## Индексация, RSS и sitemap

Production-сайт открыт для индексации:

- канонические страницы получают `index,follow`;
- `robots.txt` разрешает обход и перечисляет карты сайта;
- `sitemap.xml` содержит все канонические страницы и достоверный `lastmod`;
- дополнительно формируются `sitemap-pages.xml`, `sitemap-services.xml`, `sitemap-articles.xml`, `sitemap-cases.xml` и `sitemap-images.xml`;
- `/feed.xml` содержит новые и содержательно обновлённые юридические разборы;
- в `<head>` страниц добавляется RSS-discovery;
- ключ IndexNow публикуется отдельным текстовым файлом;
- принудительный `lock:indexing` не выполняется в production workflow и не входит в обычную команду `npm run check`.

Сценарии закрытого preview запускаются только отдельной командой:

```bash
npm run check:preview-indexing-lock
```

## IndexNow

После успешного production-деплоя и live-проверки workflow автоматически запускает IndexNow. В автоматическом режиме отправляются только URL, у которых `lastmod` совпадает с датой содержательного изменения релиза.

Ручные варианты:

```bash
INDEXNOW_CHANGED_DATE=2026-07-27 npm run submit:indexnow -- --dry-run
INDEXNOW_CHANGED_DATE=2026-07-27 npm run submit:indexnow
npm run submit:indexnow -- --all
```

## Аналитика и согласие

Аналитика в текущей итерации не удаляется:

- настроенные счётчики загружаются только после отдельного согласия;
- до согласия сторонние аналитические скрипты и события CTA не запускаются;
- отказ не ограничивает доступ к страницам и мессенджерам;
- содержание обращения, подготовленного черновика и документов в аналитику не передаётся;
- для публикаций отслеживаются только обезличенные события чтения и взаимодействия;
- для всех страниц измеряются показы CTA, клики, открытие выбора мессенджера и итоговый выбор канала связи;
- итоговая конверсия сохраняет страницу, блок, формулировку, вариант CTA, общую тему обращения, тип устройства и канал, но не персональные сведения.

Основные редакционные события: `publication_view`, `publication_scroll_25`, `publication_scroll_50`, `publication_scroll_75`, `publication_scroll_90`, `publication_scroll_100`, активное чтение, просмотр смысловых блоков, FAQ, источники, связанные материалы, переход к мессенджеру и оценка полезности.

Основные события воронки обращения:

- `cta_view` — CTA был видим пользователю не менее чем на 60%;
- `cta_click` — нажатие конкретного CTA;
- `messenger_dialog_open` — открытие выбора Telegram или WhatsApp;
- `contact_conversion` — выбор телефона, email, Telegram или WhatsApp;
- `contact_action` — вспомогательное действие, например открытие карты.

Для итоговой конверсии передаются единые поля `source_cta_id`, `source_cta_label`, `source_cta_placement` и `source_cta_variant`. Подробная схема событий, параметры и настройка целей Яндекс Метрики описаны в `docs/conversion-analytics.md`.

## Даты материалов

Для каждой страницы отдельно хранятся дата содержательной и правовой редакции и дата автоматической технической проверки. Еженедельная пересборка не изменяет `dateModified` и sitemap `lastmod`, если содержание страницы фактически не менялось.

## Автоматические проверки

Основная production-команда:

```bash
npm run check
```

Она собирает сайт и проверяет:

- обязательное прохождение актуальной таблицы и наличие session manifest при изменении контента;
- HTML и SEO-структуру;
- canonical, RSS, sitemap, robots и JSON-LD;
- географию офиса и территории услуг;
- даты материалов;
- редакционный manifest, intake-блоки и обезличенную аналитику публикаций;
- отсутствие форм, полей ввода, callback и квиза в опубликованном HTML и клиентском JavaScript;
- наличие предзаполненных прямых ссылок Telegram и WhatsApp;
- подробную аналитику CTA и итоговых обращений без текста черновика;
- доступность, мобильную версию и отсутствие горизонтальной прокрутки;
- диалог выбора мессенджера, CTA и однократную минутную подсказку;
- страницы услуг, кейсы и официальные источники;
- производительность и Core Web Vitals;
- Chromium, Firefox и WebKit;
- визуальные эталоны.

Отдельный контракт `npm run test:conversion-analytics` проверяет подключение аналитики на всех канонических страницах, события `cta_view`, `cta_click` и `contact_conversion`, атрибуцию исходного CTA и отсутствие текста подготовленного сообщения в параметрах.

Production workflow запускает именно `npm run check`, затем публикует проверенный `dist`, сверяет публичный SHA, открывает опубликованные статью и кейс, проверяет RSS, manifest и все sitemap и только после этого уведомляет IndexNow.

## Release checklist

- [ ] Для изменения контента актуальная таблица прочитана полностью, все обнаруженные вкладки перечислены в `reports/content-sessions/latest.json`.
- [ ] Изменение не включает вручную отредактированный `dist`.
- [ ] Для содержательной правки обновлены даты только затронутых страниц.
- [ ] Источники и фактический статус кейса проверены.
- [ ] Поисковый кластер, прямой ответ первого экрана, карта H2/FAQ и каннибализация проверены.
- [ ] В публичных массивах нет черновиков.
- [ ] В опубликованном HTML нет `form`, `input`, `select`, `textarea`, callback и price quiz.
- [ ] Прямые Telegram/WhatsApp-ссылки содержат предзаполненный черновик.
- [ ] Аналитика не считывает текст подготовленного сообщения и запускается только после согласия.
- [ ] `npm run check` завершён без ошибок.
- [ ] Публикуемый tree совпадает с проверенным tree.
- [ ] GitHub Pages отдаёт ожидаемый полный SHA.
- [ ] `npm run test:live` прошёл на опубликованном URL.
- [ ] `node scripts/live-all-publications-smoke.mjs` проверил все публичные материалы.
- [ ] IndexNow отправил изменённые URL либо корректно сообщил, что таких URL нет.
- [ ] Итоговый отчёт о публикации передан в чат.

## Запрещённые откаты

Без отдельного прямого решения владельца нельзя:

- возвращать формы, поля контактов, callback-dialog, квиз или серверную заявку;
- отправлять содержание обращения через сайт до самостоятельного действия пользователя в мессенджере;
- передавать в аналитику текст подготовленного сообщения, документы или введённые пользователем сведения;
- возвращать основной сайт на адрес GitHub Pages вместо `yuristshevchuk.com`;
- снова добавлять `lock:indexing` в `npm run check` или production workflow;
- смешивать адрес офиса в Химках с утверждением о наличии офиса в Москве;
- автоматически менять дату правовой редакции при технической пересборке;
- отправлять весь sitemap в IndexNow после каждой еженедельной проверки;
- публиковать статью или кейс в обход таблицы, session manifest и редакционного шлюза.
