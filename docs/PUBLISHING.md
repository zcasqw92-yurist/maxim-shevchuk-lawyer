# Штатная публикация статей и кейсов

Этот файл описывает рабочий порядок после настройки редакционного и production-конвейера. Новая публикация добавляется как структурированные данные, автоматически получает страницу, навигацию, SEO-разметку, RSS, sitemap, аналитику и проходит единый release gate.

Исторические аварии и обязательные controls: `docs/publication-failure-audit.md` и `config/publication-failure-regressions.json`. Перед любой публикацией бот обязан пройти `publication-readiness`.

## Три шлюза до создания страницы

### 1. Владелец интента

За каждым самостоятельным поисковым намерением закрепляется одна страница-владелец. В manifest указываются точный интент, URL и тип владельца, поддерживающие статьи и кейсы, проверенные конкурирующие URL, исключённые запросы, решение и причина.

### 2. Слепок выдачи

По основному запросу отдельно проверяются Яндекс и Google в нужном регионе. В каждой системе просматривается минимум пять верхних **органических результатов** и фиксируются преобладающий интент, типы страниц, локальный блок, сниппеты, пробелы конкурентов, слабые материалы, решение о типе страницы и возможность дать более практичный ответ.

Рекламные размещения не входят в обязательный органический минимум. Позиции с пометками «Реклама», «Промо», «Спонсировано», `Sponsored`, `Ad` записываются отдельно. Если сверху расположены рекламные блоки, после них всё равно изучаются минимум пять органических результатов. Слепок не должен быть старше 14 дней.

### 3. Оригинальный практический элемент

Для каждой создаваемой или существенно изменяемой страницы обязателен минимум один самостоятельный практический элемент: матрица доказательств, дерево выбора, таблица маршрутов, мини-ситуация из оплаченной практики, юридически значимые формулировки, расчёт, чек-лист, проверка договора, временная шкала, карта рисков или иной самостоятельный анализ.

## Обязательная структура статьи

Каждая статья должна содержать уникальные `id` и `slug`, `status: "published"`, рубрику, title/SEO-title/description, сильный лид и прямой ответ, минимум четыре смысловых раздела, алгоритм/доказательства/риски, минимум два FAQ, минимум два официальных HTTPS-источника, связанную услугу, даты публикации/изменения/юридической проверки, время чтения и минимум один оригинальный практический элемент.

Дополнительно: главный запрос внешне проверен; интент имеет одного владельца; H1/лид/ответ закрывают основной интент; дополнительные интенты закреплены за H2/FAQ; проверена каннибализация; тип страницы подтверждён органической выдачей; указаны запросы, которые материал не должен перехватывать.

## Обязательная структура кейса

Кейс должен содержать уникальные `id` и `slug`, подтверждённую ситуацию, изученные материалы, фактически выполненную работу, точный текущий статус, практические выводы, связанную услугу, даты и оригинальный практический элемент.

Нельзя публиковать идентификаторы клиента. Подготовленный документ нельзя описывать как выигранное дело или возвращённые деньги, если результат не подтверждён.

## Даты

- `publishedAt` меняется только при первой публикации;
- `modifiedAt` — только при содержательной правке;
- `legalReviewedAt` — только после фактической юридической перепроверки;
- техническая пересборка не обновляет содержательные даты.

## Обязательный путь бота до production

1. Создать рабочую ветку. Новые правки не вносятся напрямую в `main`.
2. Пройти актуальную таблицу, evidence/SEO/content governance и обновить session manifest.
3. Выполнить `node scripts/publication-readiness-test.mjs`. Этот gate проверяет PF-001…PF-013: единственность Pages writer, shallow Git, exact SHA marker, browser placement, recovery/watchdog, IndexNow и отсутствие старых fallback-схем.
4. Выполнить полный `npm run check` с Chromium/Firefox/WebKit до merge.
5. Создать PR. Merge разрешён только для точного head SHA, на котором полный PR CI зелёный.
6. После merge запускается единственный `Deploy GitHub Pages`: быстрый deterministic `release-check`, artifact и официальный `actions/deploy-pages`. Полный browser-heavy `npm run check` после merge повторно не запускается.
7. После успешного deploy отдельный `Verify Published Site` checkout-ит точный deployed SHA и ждёт `https://yuristshevchuk.com/deployments/<SHA>.json`.
8. Затем сверяются `build-info.json`, meta `site-build-sha`, production HTTP surface и public-copy regression всех публикаций.
9. Только после доказанного production SHA запускается IndexNow с production sitemap.
10. Завершить сессию отчётом с PR/head/merge SHA, CI, deploy, production SHA и URL.

## Автоматическое восстановление: что разрешено

Система должна исправлять внешние сбои без изменения исходников:

- **setup-only runner failure**: `Recover Pages infrastructure failure` может сделать `rerun-failed-jobs` исходного run на том же SHA; только если project code не запускался и `run_attempt < 3`;
- **production drift**: `Watch production SHA drift` раз в час сравнивает `main` и production. Если SHA различаются и штатного Pages run нет в очереди/работе, watchdog делает `workflow_dispatch` существующего `pages.yml`;
- recovery и watchdog не имеют `pages: write`, не содержат deploy-pages и не являются альтернативными deployers.

Автоматически повторять **нельзя** project/content/browser failures. Их нужно исправить в ветке и снова пройти PR CI.

**Retry-коммит**, пустой файл или служебное изменение ради нового push запрещены. В истории проекта такие commits использовались как временное восстановление, но новый контур специально устраняет эту необходимость.

## Как доказать, что публикация состоялась

Публикация считается production-ready только при последовательном подтверждении:

1. exact head SHA прошёл PR CI;
2. merge содержит проверенный head;
3. официальный Pages deployment успешен;
4. `deployments/<full-sha>.json` существует на основном домене и содержит тот же SHA;
5. `build-info.json` содержит тот же SHA;
6. главная страница содержит тот же `site-build-sha`;
7. HTTP/public-copy regression проходит для всех опубликованных материалов.

Наличие commit в `main`, зелёный build либо merge сами по себе не доказывают публикацию.

## Что создаётся автоматически

После успешной сборки формируются HTML публикаций, canonical, Open Graph, Article, Person, LegalService, BreadcrumbList, RSS, sitemap-файлы, `editorial-publications.json`, `build-info.json`, immutable `deployments/<SHA>.json` и аналитика чтения после согласия пользователя.

## Аналитика публикации

После отдельного согласия пользователя редакционные страницы могут передавать обезличенные события чтения, переходов и оценки материала. Для оценки полезности используется событие `publication_helpfulness`. Тексты обращений, документы и персональные данные не передаются. Ошибка внешнего API Метрики в post-deploy является диагностической и не отменяет уже состоявшийся deployment.

## Совместимость с будущей админкой

Будущая админка должна работать поверх этой же схемы структурированных данных, manifest, publication-readiness и публикационных проверок, а не обходить их.

## Публикационный шлюз остановит работу, если

- текущая сессия не подтверждена manifest;
- manifest не содержит все вкладки таблицы;
- не назначена единственная страница-владелец;
- отсутствуют исключённые запросы или проверенные конкурирующие URL;
- отсутствует слепок Яндекса или Google;
- в одной из систем просмотрено менее пяти органических результатов;
- рекламные размещения засчитаны в органический минимум или не записаны отдельно;
- не зафиксированы интент, типы результатов, сниппеты, пробелы и решение о типе страницы;
- проект не может дать более практичный ответ;
- у изменяемого материала отсутствует оригинальный практический элемент;
- не пройдены юридическая, фактическая или анонимизационная проверки;
- `dist` изменён вручную;
- publication-readiness обнаружил старую аварийную архитектуру;
- `npm run check` завершён с ошибкой;
- PR head SHA не имеет зелёного полного CI.
