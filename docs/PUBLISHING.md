# Штатная публикация статей и кейсов

Этот файл описывает рабочий порядок после настройки редакционного конвейера. Новая публикация добавляется как структурированные данные, автоматически получает страницу, навигацию, SEO-разметку, RSS, sitemap, аналитику и проходит единый release gate.

- ID: `1W4014FzdUJWYDja7VUh5XXUsSuxtQIrcS5fWRX1rm24`;
- основной вход: `gid=83276506`;
- высший приоритет внутри редакционного процесса;
- обязательный живой просмотр всех вкладок перед каждой контентной сессией.

Полный договор процесса находится в `AGENTS.md`, `docs/content-governance.md` и `config/content-governance.json`. При изменении контентного файла в том же наборе изменений обязателен `reports/content-sessions/latest.json`.

Контракт проверяется командой:

```bash
npm run test:content-governance
```

Если таблица недоступна, вкладка пропущена, один из трёх шлюзов кластера не заполнен или manifest отсутствует, материал не переносится в публичные массивы.

## Где хранится контент

- статьи: `src/editorial-data.mjs`, массив `articles`;
- полные кейсы: `src/editorial-data.mjs`, массив `practiceCases`;

## Три шлюза до создания страницы

### 1. Владелец интента

За каждым самостоятельным поисковым намерением закрепляется одна страница-владелец. В manifest указываются точный интент, URL и тип владельца, поддерживающие статьи и кейсы, проверенные конкурирующие URL, исключённые запросы, решение и причина.

### 2. Слепок выдачи

По основному запросу отдельно проверяются Яндекс и Google в нужном регионе. В каждой системе просматривается минимум пять верхних **органических результатов** и фиксируются:

- преобладающий органический интент;
- типы органических страниц;
- локальный блок;
- повторяющиеся формулировки органических сниппетов;
- пробелы конкурентов;
- устаревшие или слабые материалы;
- решение о типе страницы;
- возможность дать более практичный ответ.

Рекламные размещения не входят в обязательный органический минимум. Позиции с пометками «Реклама», «Промо», «Спонсировано», `Sponsored`, `Ad` и аналогичными обозначениями записываются отдельно: количество, фактические пометки, типы рекламодателей и повторяющиеся предложения.

Если сверху расположены рекламные блоки, после них всё равно изучаются минимум пять органических результатов. Слепок не должен быть старше 14 дней.

### 3. Оригинальный практический элемент

Для каждой создаваемой или существенно изменяемой страницы обязателен минимум один самостоятельный практический элемент: матрица доказательств, дерево выбора, таблица маршрутов, мини-ситуация из оплаченной практики, юридически значимые формулировки, расчёт, чек-лист, проверка договора, временная шкала, карта рисков или другой самостоятельный анализ.

В manifest указываются польза, пробел органической выдачи, внутренние ID источников, основание и точное место элемента.

## Обязательная структура статьи

Каждая статья должна содержать:

- уникальные `id` и `slug`;
- `status: "published"`;
- рубрику, заголовок, SEO-заголовок и description;
- сильный лид и короткий прямой ответ;
- не менее четырёх смысловых разделов;
- алгоритм, доказательства, риски или ошибки;
- не менее двух FAQ;
- не менее двух официальных HTTPS-источников;
- связанную услугу;
- даты публикации, изменения и юридической проверки;
- время чтения;
- при наличии связанный подтверждённый кейс;
- минимум один оригинальный практический элемент.

Дополнительно:

- главный запрос внешне проверен;
- основной интент имеет единственного владельца;
- H1, лид и короткий ответ закрывают основной интент на первом экране;
- дополнительные интенты закреплены за H2 или FAQ;
- проверена каннибализация;
- тип страницы подтверждён органической выдачей;
- указаны запросы, которые материал не должен перехватывать.

## Обязательная структура кейса

Кейс должен содержать уникальные `id` и `slug`, подтверждённую ситуацию, изученные материалы, фактически выполненную работу, точный текущий статус, практические выводы, связанную услугу, даты и оригинальный практический элемент.

Нельзя публиковать идентификаторы клиента. Подготовленный документ нельзя описывать как выигранное дело или возвращённые деньги, если результат не подтверждён.

## Даты

- `publishedAt` меняется только при первой публикации;
- `modifiedAt` — только при содержательной правке;
- `legalReviewedAt` — только после фактической юридической перепроверки;
- техническая пересборка не обновляет содержательные даты.

## Порядок публикации

1. Получить текущие метаданные таблицы и динамический список вкладок.
2. Пройти все вкладки, диапазоны, заметки и контрольные показатели.
3. Зафиксировать источники по полным ID и отделить факты от гипотез.
4. Назначить владельцев интентов, проверить существующие URL и исключённые запросы.
5. Выполнить слепок органической выдачи Яндекса и Google.
6. Рекламные размещения записать отдельно и не включать в органический минимум.
7. После слепка проверить Wordstat и сформировать карту «запрос → H2/FAQ».
8. Назначить оригинальный практический элемент.
9. Создать или обновить `reports/content-sessions/latest.json` schemaVersion 3.
10. Добавить или изменить объект статьи/кейса и даты.
11. Проверить право, источники, статус и анонимизацию.
12. Запустить:

```bash
npm run check
```

13. Исправить все ошибки; тесты и пороги не ослаблять.
14. Создать PR и дождаться полного production-CI.
15. После merge GitHub Pages повторно запускает `npm run check`.
16. Live-smoke сверяет публичный SHA, маршруты и все публикации.
17. IndexNow получает только новые и действительно изменённые URL.
18. Завершить сессию отчётом в чате.

## Что создаётся автоматически

После успешной сборки формируются HTML публикаций, canonical, Open Graph, Article, Person, LegalService, BreadcrumbList, RSS, sitemap-файлы, `editorial-publications.json` и аналитика чтения после согласия пользователя.

## Аналитика публикации

После отдельного согласия пользователя редакционные страницы могут передавать обезличенные события чтения, переходов и оценки материала. Для оценки полезности используется событие `publication_helpfulness`. Тексты обращений, документы и персональные данные не передаются.

## Совместимость с будущей админкой

Будущая админка должна работать поверх этой же схемы структурированных данных, manifest и публикационных проверок, а не обходить их.

## Публикационный шлюз остановит сборку, если

- текущая сессия не подтверждена manifest;
- manifest не содержит все вкладки таблицы;
- не назначена единственная страница-владелец;
- отсутствуют исключённые запросы или проверенные конкурирующие URL;
- отсутствует слепок Яндекса или Google;
- в одной из систем просмотрено менее пяти органических результатов;
- рекламные размещения засчитаны в органический минимум;
- рекламные размещения не записаны отдельно;
- не зафиксированы органический интент, типы результатов, сниппеты, пробелы и решение о типе страницы;
- проект не может дать более практичный ответ;
- у изменяемого материала отсутствует оригинальный практический элемент;
- не пройдены юридическая, фактическая или анонимизационная проверки;
- `dist` изменён вручную;
- `npm run check` завершён с ошибкой.
