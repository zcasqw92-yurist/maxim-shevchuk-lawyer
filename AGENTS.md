# Обязательный протокол подготовки и публикации контента

Эти инструкции действуют для всего репозитория и имеют высший приоритет внутри редакционного процесса проекта.

## Обязательный publication-readiness протокол бота

Любая правка сайта — контент, CSS, JS, SEO, workflow, analytics, service page или инфраструктура — проходит один и тот же безопасный путь:

**рабочая ветка → publication-readiness → полный PR CI → merge проверенного SHA → один штатный Pages deploy → immutable SHA marker → production HTTP/public-copy verification → IndexNow.**

Боту запрещено считать запись в `main` публикацией. Публикация доказана только когда основной домен отдаёт точный SHA проверенного merge через `deployments/<full-sha>.json`, `build-info.json` и meta `site-build-sha`.

До открытия/слияния PR бот обязан:

1. Работать в отдельной ветке. Не вносить новую работу напрямую в `main`.
2. Запустить ранний инфраструктурный шлюз `node scripts/publication-readiness-test.mjs` либо обязательный `node scripts/release-check.mjs`, который включает его первым.
3. Убедиться, что полный PR CI относится к точному head SHA и завершён зелёным. Нельзя сливать более новый непроверенный head.
4. Не ослаблять tests, thresholds, permissions и production invariants ради прохождения конкретной правки.
5. Не добавлять второй Pages deployer, fallback с `pages: write`, собственный Pages REST client или `cancel-in-progress:true` для production Pages.
6. Не переносить browser-heavy проверки после deploy: Chromium/Firefox/WebKit должны доказать поведение до merge. Полный PR-CI сохраняет `scripts/live-all-publications-smoke.mjs` как all-publications browser regression до merge, но этот smoke не запускается повторно после публикации.
7. Не использовать технический retry-коммит или пустой файл для повторного запуска публикации.

Если публикация не прошла, бот сначала классифицирует сбой:

- **setup-only hosted runner failure** — project code не запускался; допускается ограниченный автоматический `rerun-failed-jobs` того же run и того же SHA, максимум пока `run_attempt < 3`;
- **project/content/browser failure** — автоматический retry запрещён; найти причину, исправить в ветке, повторить PR CI;
- **Pages/backend failure** — не создавать альтернативный deployer; использовать только повтор/dispatch штатного `Deploy GitHub Pages`;
- **production SHA drift** — hourly watchdog сравнивает `main` и production и dispatch-ит штатный Pages workflow без изменения Git;
- **post-deploy verification failure** — сначала определить, опубликован ли точный SHA; не смешивать уже состоявшийся deployment с ошибкой последующей диагностики;
- **Metrica/API telemetry failure** — диагностическая внешняя ошибка не должна делать опубликованный сайт «не опубликованным».

Исторические причины PF-001…PF-014 перечислены в `docs/publication-failure-audit.md`; их machine regression должен оставаться зелёным перед каждой новой публикацией.

## Жёсткий шлюз таблицы перед любой правкой

Перед **любой** новой статьёй, правкой сайта, SEO или инфраструктуры бот обязан заново открыть живую Google-таблицу, сначала `00_Старт`, затем вкладку `29_Публикационный_шлюз` (gid `290000290`). Это правило действует даже для изменения, которое не является контентным.

1. До merge заполнить в шлюзе тип изменения, объект/URL/scope и текущие branch / PR / head SHA.
2. Каждый обязательный `PUB-*` пункт переводить в `ПРОЙДЕНО` только после появления проверяемого доказательства: команды, CI run, SHA, URL или результата production-проверки. Статус **не может быть выставлен по предположению**, по памяти или только потому, что аналогичная проверка когда-то проходила.
3. Условный пункт получает `Н/П` только когда он действительно неприменим к текущему изменению; обязательный блокер нельзя обходить через `Н/П`.
4. Merge запрещён, пока pre-merge статус `29_Публикационный_шлюз!B2` не равен `MERGE РАЗРЕШЕН`. B2 учитывает только доказательства, которые объективно могут существовать до merge; post-deploy результаты не могут быть условием самого merge. Нельзя вручную подменять формулу итогового статуса.
5. После merge публикация не считается завершённой, пока `29_Публикационный_шлюз!L2` не равен `ПУБЛИКАЦИЯ ЗАВЕРШЕНА`. L2 достигается только после подтверждённых exact production SHA, HTTP/public-copy и результата IndexNow; затем в секцию `ЖУРНАЛ РЕЛИЗОВ` добавляется строка с branch/PR, head SHA, merge SHA, production SHA и результатами проверок. Pre-merge разрешение B2 само по себе не является доказательством публикации.
6. Если обнаружен ранее неизвестный тип сбоя, в `J2` ставится `Да — не закрыт`; задача и публикационная сессия не закрываются. Сначала создаётся следующий `PF-015+`, фиксируются root cause и evidence, добавляется machine regression или строго ограниченный recovery, после чего весь шлюз повторяется на новом проверенном SHA. Только тогда допустимо `Да — закрыт regression`.
7. История PF-001…PF-014 на вкладке является постоянным запретом на возврат этих архитектур. Удаление или обход этого раздела не является исправлением.

Для видимого контента `29_Публикационный_шлюз` одновременно входит в динамически обнаруженный полный список вкладок публикационной сессии и должен быть отражён в `reports/content-sessions/latest.json`. Для неконтентной правки session manifest может быть неприменим, но живой публикационный шлюз всё равно обязателен.

## До написания контента

1. Открыть актуальную таблицу и получить её текущие метаданные.
2. Динамически получить полный перечень вкладок. Нельзя ограничиваться сохранённым в репозитории базовым списком.
3. Последовательно просмотреть **каждую** вкладку, включая служебные, контрольные, импортные, статистические и пустые по данным вкладки.
4. На каждой вкладке проверить все непустые используемые строки и столбцы, заголовки, пояснения, заметки/комментарии, статусы, связи и контрольные показатели.
5. Отобрать источники для конкретного материала по полным ID. Не переносить в репозиторий полные диалоги, персональные данные и лишние детали клиентов.
6. Отделить факты от гипотез. Наличие записи в `02_ЮрДоки` подтверждает оплаченную юридическую работу, но само по себе не подтверждает точную сумму, дату и способ оплаты либо положительный результат дела.
7. Для статьи пройти SEO-шлюз таблицы: язык клиента → поисковая гипотеза → внешняя проверка спроса и выдачи → главный интент → прямой ответ первого экрана → карта «запрос → H2/FAQ» → проверка покрытия и каннибализации.
8. До решения о новой странице пройти три обязательных шлюза подготовки кластера:
   - **владелец интента**: за самостоятельным намерением закрепляется ровно одна страница-владелец; указываются поддерживающие материалы, подтверждающие кейсы, проверенные конкурирующие URL сайта и запросы, которые этой странице запрещено забирать;
   - **слепок выдачи**: отдельно фиксируются Яндекс и Google, регион, запрос и не менее пяти верхних **органических результатов** в каждой системе. Рекламные размещения с пометками «Реклама», «Промо», «Спонсировано», `Sponsored`, `Ad` и аналогичными обозначениями в обязательную пятёрку не входят. Они записываются отдельно как коммерческий фон: количество, фактическая пометка, типы рекламодателей и повторяющиеся предложения;
   - **оригинальный практический элемент**: для каждого изменяемого материала указывается хотя бы один конкретный элемент, основанный на реальных обращениях, оплаченной практике, доказательствах, расчёте или самостоятельном правовом анализе и закрывающий выявленный пробел органической выдачи.
9. Если по органическому слепку выдачи нельзя дать существенно более практичный ответ, новая страница не создаётся: материал переносится в H2/FAQ существующей страницы, кейс либо откладывается.
10. Для кейса раздельно подтвердить выполненную работу, результат процедуры и результат дела. Подготовленный документ или отправленное обращение нельзя называть выигранным делом.
11. До изменения контентных файлов создать или обновить `reports/content-sessions/latest.json` по шаблону `reports/content-sessions/template.json`.
12. Перед публикацией каждой новой или изменённой статьи выполнить обязательную проверку публичного текста командой `npm run test:public-copy`. Проверка одновременно охватывает новую статью и все ранее опубликованные статьи в исходных данных. Публикация блокируется при внутренних SEO-терминах, редакционных пояснениях, внутренних ID, упоминаниях происхождения материала или черновых артефактах.

Если актуальная таблица недоступна, хотя бы одна вкладка не проверена, любой из трёх шлюзов не заполнен либо предпубликационный контроль публичного текста не пройден, публикация блокируется. Разрешено сохранить отдельный черновик вне публичных массивов, но нельзя добавлять его в production-контент.

## Где находится контент

Основные контентные источники перечислены в `config/content-governance.json`. Папка `dist` является результатом сборки и вручную не редактируется.

Каждая публикационная сессия обязана оставлять проверяемый след:

- время и версия таблицы;
- фактически обнаруженный полный список вкладок;
- диапазон проверки каждой вкладки;
- использованные ID источников без персональных данных;
- карта интентов и результаты внешней SEO-проверки;
- единственная страница-владелец каждого интента и запрещённые для неё запросы;
- слепок органической выдачи Яндекса и Google;
- рекламные размещения, зафиксированные отдельно и не засчитанные в органический минимум;
- оригинальный практический элемент каждого материала и его основание;
- юридическая, фактическая и анонимизационная проверки;
- результат предпубликационной проверки публичного текста новой и прежних статей;
- изменённые файлы и ожидаемые публичные URL.

## После подготовки и публикации

1. До merge запустить полный контракт:

   ```bash
   node scripts/publication-readiness-test.mjs
   npm run check
   ```

2. Не ослаблять тесты и пороги ради конкретной публикации.
3. Сливать только точный head SHA, для которого полный PR CI завершён успешно.
4. После merge дождаться `Deploy GitHub Pages`; сам deploy и последующий `Verify Published Site` являются разными стадиями.
5. Post-deploy автоматически сначала проверяет immutable `deployments/<SHA>.json`, затем `build-info.json` и SHA главной страницы, после чего выполняет HTTP/public-copy regression всех публикаций.
6. Публикация не считается завершённой, пока production не подтвердил точный SHA, regressions не прошли и L2 живого табличного шлюза не показывает `ПУБЛИКАЦИЯ ЗАВЕРШЕНА`.
7. Если setup-only recovery и watchdog не восстановили внешнюю инфраструктуру, зафиксировать точный класс сбоя; не создавать retry-коммит.
8. После завершения дать в чате отчёт: что изучено, что создано/изменено, PR/head/merge SHA, результаты CI/deploy/production SHA, какие URL проверены, что не опубликовано и почему.
9. В каждом отчёте отдельно написать результат контроля прежних статей: либо замечаний нет, либо перечислить каждый URL, проблемную фразу/блок, исправление и результат повторной проверки.

## Запрещено

- пропускать вкладки таблицы;
- выдавать поисковую гипотезу за подтверждённый запрос;
- создавать отдельные страницы под вариации одной формулировки без самостоятельного интента;
- назначать одному интенту несколько страниц-владельцев;
- публиковать материал без слепка органической выдачи Яндекса и Google;
- засчитывать рекламные или спонсируемые позиции в обязательные пять органических результатов;
- смешивать органические результаты и рекламные размещения в одном счётчике;
- считать обычный пересказ конкурентов оригинальной практической ценностью;
- подменять язык клиента искусственным перечнем ключей;
- переносить в публичную статью внутреннюю SEO-терминологию, редакционные комментарии, служебные ID, описание оплаченной практики как источника текста или черновые инструкции;
- придумывать оплату, результат, документы, даты или обстоятельства;
- считать молчание клиента доказанным отказом;
- публиковать идентификаторы и персональные данные;
- редактировать `dist` вручную;
- вносить новую работу напрямую в `main` в обход PR-CI;
- использовать пустой retry-коммит для лечения Actions/Pages инфраструктуры;
- добавлять альтернативный Pages writer или browser-heavy deploy fallback;
- обходить или вручную подменять формулы B2/L2 `29_Публикационный_шлюз`;
- завершать публикационную сессию без полного самотеста, точного production SHA, регрессионной проверки прежних статей, записи в `ЖУРНАЛ РЕЛИЗОВ` и отчёта пользователю.
